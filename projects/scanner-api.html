오토스캐너 연계 API

C# 윈도우 클라이언트·Kotlin PDA 앱과 택배사 기간계를 연결하는 Kotlin·Spring 미들웨어

주요 업무 · 택배 현장 시스템 연계인수 후 유지보수·기능 추가

  • Kotlin
  • Spring Framework 5
  • WebClient
  • MyBatis · MariaDB
  • EC2 · Tomcat
OVERVIEW

프로젝트 개요

기존 Kotlin·Spring 오토스캐너·PDA 연계 API를 인수받아 유지보수했습니다. 택배사 연계 방식 변경에 맞춰 SOAP 통신을 REST API로 전환하고, 수천 건의 바코드 스캔 목록을 500건씩 나눠 전송하도록 개선했습니다.

SCOPE

담당 업무 및 개발 내용

기존 Kotlin·Spring API를 인수받아 유지보수하고 기능을 개선했습니다. 직접 수행한 변경은 택배사 연계 방식의 SOAP→REST 전환과 스캔 목록의 500건 단위 분할 전송입니다. C# 윈도우 클라이언트와 Kotlin PDA 앱이 보내는 스캔 데이터의 입력·중복 검사, 이력 저장·조회와 항목별 전송 결과 처리는 기존 시스템의 유지보수 범위입니다.

FEATURE 01 구현·유지보수

스캔 수집·저장

C# 윈도우 클라이언트와 Kotlin PDA 앱이 전송한 바코드 스캔 데이터의 운송장·시각·업무 정보를 검사하고 이력으로 저장합니다.

PROBLEM

문제

장비에서 한 번에 여러 스캔 결과가 들어오며, 누락된 필드나 동일 업무의 중복 항목을 구분해야 합니다.

SOLUTION

해결

스캔 요청 목록의 필수 값과 형식을 검사하고 요청 내부 및 기존 이력의 중복을 확인합니다. 저장할 항목을 추려 DB에 적재하고 지점의 자동·수동 전송 설정에 따라 처리 흐름을 나눕니다.

설계 이유와 트레이드오프

현장 이력과 외부 전송을 구분

스캔 이력을 먼저 저장하고 기간계 전송을 이어가는 구조입니다. 현장 기록을 조회할 수 있지만 DB 저장과 외부 전송은 하나의 트랜잭션으로 묶이지 않으므로 저장 여부와 전송 결과를 각각 다뤄야 합니다.

업무와 운송장을 기준으로 사전 중복 확인

같은 운송장이라도 업무 단계가 다르면 별도 스캔일 수 있어 업무 구분을 함께 사용합니다. 사전 중복 검사는 잘못된 반복 입력을 걸러내는 데 활용하며, 동시 재요청까지 다루려면 멱등 기준과 DB 제약을 함께 정해야 합니다.

RESULT

기존 API의 제공 기능

기존 API의 입력 검사·중복 확인·이력 저장과 자동·수동 전송 분기 기능을 유지보수합니다.

FEATURE 02 직접 수행한 연계 개선

REST 전환·분할 전송

택배사의 SOAP→REST 연계 변경에 대응하고, 대량 스캔 목록을 500건 단위 요청으로 나눠 전송하도록 개선했습니다.

PROBLEM

문제

택배사 서버의 연계 방식이 SOAP에서 REST로 변경됐습니다. 현장 클라이언트는 수천 건의 스캔 데이터를 한 번에 요청할 수 있어 외부 서버로 보낼 요청 크기도 나눠야 했습니다.

SOLUTION

해결

기존 SOAP 통신을 택배사 REST API의 요청·응답 형식으로 변경해 연동했습니다. 수신한 스캔 목록은 500건 단위로 분할해 전송하도록 개선했습니다. WebClient·Reactor 전송 경로의 동시 요청 제한과 항목별 결과 취합은 시스템의 기존 처리 구조를 살피며 유지보수하는 범위로 구분합니다.

설계 이유와 트레이드오프

요청 크기와 동시 실행은 별도 제어

500건 단위 분할은 한 HTTP 요청에 담는 데이터 크기를 제한하는 변경입니다. 동시에 실행하는 HTTP 요청 수 제한, 저장 이력의 중복 선조회는 각각 별개의 문제이며 분할 전송만으로 동시 중복 처리를 방지하지는 않습니다.

외부 규격 변경을 서버에서 수용

현장 클라이언트의 스캔 데이터를 서버에서 택배사 REST 규격으로 매핑했습니다. 기존 결과 취합 흐름을 유지하면서 요청 필드와 응답 해석을 함께 관리해야 하며, 결과를 취합하는 API 응답 시간에는 외부 서버의 처리 시간도 포함됩니다.

RESULT

기존 API의 제공 기능

SOAP→REST 연계 전환과 요청당 500건 분할 전송을 수행했습니다. 배치별 전송 결과를 취합한 뒤 호출자에게 최종 응답을 반환합니다.

FEATURE 03 구현·유지보수

전송 결과·이력 조회

스캔 기록과 항목별 전송 결과를 연결하고, 기간·지점 조건의 조회와 집계를 제공합니다.

PROBLEM

문제

여러 운송장을 보낸 요청에서 일부만 실패하거나 응답에 특정 항목이 빠질 수 있습니다. HTTP 응답 하나만으로 각 스캔의 전송 결과를 판단하기 어렵습니다.

SOLUTION

해결

기간계 응답을 전송한 운송장 목록과 대조하고 응답이 없는 항목은 실패로 분류합니다. 항목별 결과를 DB 갱신과 성공·실패 취합에 사용하며, 스캔 이력은 이미지 포함·제외 조회와 페이징, 일별·월별 집계로 제공합니다.

설계 이유와 트레이드오프

요청 전체와 항목별 결과를 따로 판단

응답이 도착했더라도 항목마다 성공 여부가 다를 수 있어 목록 단위로 대조합니다. 전송 응답과 결과 저장도 별도 처리이므로 외부 성공 이후 DB 갱신 실패에 대비한 결과 대조·재처리 기준이 필요합니다.

조회 목적에 따라 이미지와 목록 분리

현장 확인에는 이미지가 필요하지만 목록·집계에서는 모든 이미지가 필요하지 않습니다. 이미지 포함 여부와 페이징을 구분해 사용 목적에 맞는 조회를 제공하고, 날짜·지점 조건으로 이력을 찾도록 구성합니다.

RESULT

기존 API의 제공 기능

항목별 전송 응답 대조와 결과 취합, 스캔 이력의 이미지 포함·제외 페이징 및 일별·월별 조회 기능을 제공합니다.

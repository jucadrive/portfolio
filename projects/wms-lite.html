WMS-Lite

OVERVIEW

프로젝트 개요

동시에 들어오는 주문에서 재고가 초과 예약되지 않도록 할당 로직을 개발했습니다. DB 접근을 최적화하고 Redis Lua로 품절 요청을 먼저 처리했으며, 향후 비동기 연계를 위한 Kafka·Outbox 발행 흐름을 구현했습니다.

SCOPE

담당 업무 및 개발 내용

상품·창고·재고·주문·할당 모듈로 구성한 단일 애플리케이션에서 재고 예약과 DB 접근 최적화를 구현했습니다. Redis 선예약과 실패 시 수량 반환, Transactional Outbox와 Kafka 발행·수신을 추가하며 부하와 장애 상황을 실험했습니다.

FEATURE 01 구현 완료

원자적 재고 예약

가용 재고 검사와 예약 수량 갱신을 하나의 DB 연산으로 처리합니다.

PROBLEM

문제

여러 요청이 같은 재고를 조회한 뒤 각각 수량을 갱신하면 보유량을 초과해 예약할 수 있습니다.

SOLUTION

해결

가용 수량 조건을 UPDATE에 포함하고 갱신된 행 수로 예약 성공 여부를 판단합니다. 예약 이후의 주문·할당 저장도 같은 트랜잭션으로 묶었습니다.

설계 이유와 트레이드오프

재고 판단을 DB의 조건부 갱신에 맡기기

조회와 갱신 사이의 경쟁을 줄이고 DB를 최종 재고 기준으로 유지합니다. 동일 재고 행에 요청이 집중되면 행 잠금과 트랜잭션 점유에 따른 경합은 여전히 발생합니다.

VALIDATION

구현 결과와 테스트

재고 100개에 3,000건을 요청하는 부하 실험에서 예약 성공 100건, 품절 2,900건, 예상하지 못한 오류 0건을 기록했습니다.

FEATURE 02 구현 완료

DB 접근 최적화

예약부터 커밋까지 불필요한 조회와 추가 상태 갱신을 줄였습니다.

PROBLEM

문제

같은 재고에 요청이 집중될 때 예약 이후의 불필요한 DB 작업도 트랜잭션 점유 시간을 늘렸습니다.

SOLUTION

해결

상품·창고는 getReferenceById로 연결하고 재고는 ID만 조회했습니다. 주문 상태를 저장 전에 변경해 최초 INSERT에 반영했습니다.

설계 이유와 트레이드오프

연결에 필요한 정보만 사용

전체 엔티티의 값이 필요하지 않은 연결에는 ID와 지연 참조를 사용했습니다. 불필요한 조회를 줄일 수 있지만 참조 대상의 유효성과 지연 조회가 발생하는 시점을 이해해야 합니다.

VALIDATION

구현 결과와 테스트

100 VUs·1,000요청 조건에서 5회 실험의 중앙값 기준 RPS가 2,420.09에서 3,380.82로 증가하고 p95 응답 시간이 225.47ms에서 149.28ms로 줄었습니다.

FEATURE 03 구현 완료 · 복구 실험 중

Redis 선예약

품절 요청을 Redis에서 먼저 처리하고 성공 후보만 DB 예약으로 넘깁니다.

PROBLEM

문제

재고가 소진된 뒤에도 모든 요청이 같은 DB 행에 도달해 경합을 일으켰습니다.

SOLUTION

해결

Lua로 가용 수량 검사와 차감을 원자적으로 처리한 뒤 DB 예약을 실행합니다. DB 처리 중 예외가 발생하면 Redis 수량 반환을 시도합니다.

설계 이유와 트레이드오프

Redis는 품절 처리, DB는 최종 예약 판단

Redis로 품절 요청을 먼저 걸러내되 DB의 조건부 예약을 유지했습니다. 두 저장소 사이에는 원자적 커밋이 없으므로 프로세스 중단과 보상 실패에 대비한 재고 재동기화가 필요합니다.

VALIDATION

구현 결과와 테스트

300 VUs·3,000요청·초기 재고 100개 조건의 5회 실험에서 RPS 중앙값은 7,454.87, p95는 42.79ms였습니다. 각 실행에서 예약 성공 100건과 품절 2,900건을 유지했습니다.

FEATURE 04 구현 완료 · 복구 실험 중

Kafka·Outbox

할당 결과를 DB에 저장한 뒤 Kafka로 발행해 비동기 연계의 기반을 마련했습니다.

PROBLEM

문제

할당 저장과 Kafka 전송을 요청에서 각각 처리하면 DB 커밋 후 전송 실패 시 이벤트를 잃을 수 있습니다.

SOLUTION

해결

할당 결과와 Outbox 이벤트를 같은 트랜잭션에 저장했습니다. 별도 Publisher가 미발행·실패 이벤트를 조회해 Kafka로 전송하고 상태를 갱신합니다. Consumer는 현재 이벤트 수신 로그까지 구현했습니다.

설계 이유와 트레이드오프

단일 애플리케이션에서 후속 연계 준비

현재 구조는 MSA가 아닌 모듈형 단일 애플리케이션입니다. 할당은 동기 DB 트랜잭션으로 유지하고 이벤트 발행만 분리해 향후 알림·배송 연동 같은 후속 작업을 연결할 수 있도록 했습니다.

재발행과 중복 수신 고려

Kafka 전송 직후 DB 상태 갱신 전에 중단되면 동일 이벤트가 다시 발행될 수 있습니다. 재시도로 미발행 이벤트를 처리하는 대신 소비자의 멱등 처리와 재시도 정책을 보완해야 합니다.

VALIDATION

구현 결과와 테스트

Kafka를 중단해도 할당 API가 성공하고 미발행 이벤트가 DB에 남는 것을 확인했습니다. Kafka 복구 후 발행 상태 전환과 Consumer 수신 로그를 점검했습니다. 부하 실험 후 생성된 이벤트 100건의 발행 완료도 확인했습니다.

04 / REFLECTION

개발 회고와 개선 방향

회고

재고 할당에서는 처리량을 높이면서도 예약 합계가 보유량을 넘지 않는지 함께 살펴야 했습니다. DB 접근을 줄이고 Redis로 품절 요청을 걸러낸 뒤 Outbox를 추가하면서, 요청 경로의 성능과 후속 이벤트 처리의 신뢰성을 나누어 설계하는 경험을 쌓았습니다.

NEXT / 향후 계획

향후 개선 방향

Consumer 멱등 처리, 중복 이벤트, 재시도·backoff와 DLQ를 실험할 계획입니다. Redis와 DB의 수량이 어긋나는 상황을 재현하고 재동기화 절차도 보완하려 합니다.

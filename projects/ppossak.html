OVERVIEW

프로젝트 개요

직접 구매한 센서 키트로 회로를 만들고, 수온을 보정한 영양액 TDS(ppm)를 Android 앱에서 확인하는 개인 서비스입니다. 집의 수질을 확인하려던 센서 선택 착오를 수경재배 용도로 전환하고, 에이전트 하네스로 펌웨어·백엔드·앱을 개발해 미니 PC에 배포했습니다.

SCOPE

담당 업무 및 개발 내용

TDS·온도 센서와 ESP32·ADS1115를 직접 구매해 빵판과 점퍼 케이블로 회로를 조립하고, 개인 미니 PC에 서버를 배포했습니다. 제품 목표·핵심 설계·인수 조건을 정하고 AGENTS.md와 Harness.md로 작업 범위·검증·중단 기준을 구성했습니다. 에이전트와 C 펌웨어, Java·Spring Boot 백엔드, Kotlin·Compose 앱을 개발하며 구현 결과와 실물 연동을 검수했습니다.

FEATURE 01 도메인 전환·구현

센서 선택과 전환

집의 수질이 의심돼 시작했지만, 구매한 센서가 관측하는 범위에 맞춰 수경재배 서비스로 목적을 바꿨습니다.

PROBLEM

문제

처음에는 TDS 센서로 수돗물이나 배관의 이상을 확인하려 했습니다. 구매 후 측정 지표를 검토하면서 TDS만으로 녹 입자·탁도나 식수의 안전성을 판단할 수 없다는 점을 확인했습니다. 초기 목적과 센서 선택이 맞지 않았습니다.

SOLUTION

해결

이미 만든 ESP32 측정·MQTT 전송·DB 저장 기반을 재사용해, 수경재배 영양액의 TDS 추세와 물 관리 이력을 함께 기록하는 서비스로 전환했습니다. 재배 등록·종료와 물 교체·보충·영양제 추가 기록을 측정 세션에 연결했습니다.

설계 이유와 트레이드오프

센서가 관측하는 범위에서 문제를 다시 정의

구매 착오를 감추기보다 센서가 알려줄 수 있는 정보와 생활 속 활용처를 다시 찾았습니다. 영양액 농도 변화와 직접 수행한 관리 기록을 보여주고, 식물 건강이나 물 교체 시점을 센서값 하나로 단정하는 기능은 넣지 않았습니다.

기존 측정 자산과 기록 재사용

측정 펌웨어·통신·원본·통계는 유지하고 재배 도메인을 추가했습니다. 과거 측정도 그대로 조회할 수 있도록 재배 연결 전후의 기록을 구분했습니다.

RESULT

개발 결과

수질 확인용으로 출발한 측정 시스템을 재배별 TDS 기록과 물 관리 이력을 제공하는 개인 Android 서비스로 전환했습니다. 실물 센서와 기존 측정 데이터를 유지하면서 사용할 목적을 바꿨습니다.

FEATURE 02 실물 정상 경로 확인

회로·수온 보정

센서와 보드를 직접 구입하고 배선해, 고정 수온 가정 대신 실제 수온으로 보정한 ppm을 표시합니다.

PROBLEM

문제

TDS 전압만 읽고 수온을 고정값으로 가정하면 실제 수온이 달라져도 같은 조건으로 환산하게 됩니다. 실물 센서 연결뿐 아니라 온도 값의 유효 범위와 측정 시점도 함께 다뤄야 했습니다.

SOLUTION

해결

ESP32, SEN0244 TDS 센서, ADS1115, DS18B20을 빵판과 점퍼 케이블로 연결했습니다. C·ESP-IDF 펌웨어에서 실측 수온을 이용해 전압을 25°C 기준으로 보정한 뒤 TDS ppm을 계산하고, 원래 전압·수온·측정 시점도 서버에 보존합니다.

설계 이유와 트레이드오프

수온이 없거나 오래됐을 때 임의의 값으로 대체하지 않기

유효 범위와 측정 시점을 확인한 수온만 계산에 사용합니다. 센서 오류나 오래된 온도를 정상 측정처럼 처리하지 않고, 측정 시작을 막거나 이미 수집한 원본을 불완전 세션으로 남기도록 했습니다.

온도 보정과 센서 교정 구분

실측 수온을 25°C 기준으로 환산하는 기능과 표준액으로 센서를 교정하는 작업을 구분했습니다. 앱 상세에서 실측·모의·과거 가정 수온과 보정 정보를 따로 표시하며, 표준액 교정은 후속 과제로 남겼습니다.

RESULT

개발 결과

DS18B20 실물 측정부터 온도 보정, MQTT 전송, 서버 보존, 앱 표시와 장비 버퍼 해제까지 정상 경로를 한 차례 확인했습니다. 표준액 교정과 기준 온도계 대비 정확도 비교는 향후 진행할 작업입니다.

FEATURE 03 구현·통합 테스트

전송·원본 보존

MQTT 전송 성공과 DB 저장 완료를 구분하고, 서버의 보존 확인을 받은 뒤 장비 원본을 해제합니다.

PROBLEM

문제

장비가 메시지를 보냈다는 이유만으로 원본을 지우면, 서버 저장 실패 때 측정값을 잃을 수 있습니다. 재전송된 데이터가 기존 원본과 다르거나 측정 도중 센서가 실패하는 경우도 구분해야 했습니다.

SOLUTION

해결

세션과 원본을 하나의 DB 트랜잭션으로 저장하고 실제 커밋이 끝난 후 MQTT 보존 확인을 보냅니다. 장비는 확인 전까지 원본을 보관합니다. 동일 세션·순번의 재수신은 원본과 비교해 중복과 충돌을 구분하고, 기존 원본을 덮어쓰지 않도록 했습니다.

설계 이유와 트레이드오프

원본 보존과 통계 대상 분리

정상 세션의 원본 60개는 모두 보존하되 초기 안정화 10개를 제외한 50개로 통계를 계산합니다. 수집 도중 끊긴 세션도 원본을 남기고 정상 추세와 구분합니다.

통신 확인과 저장 확인을 별도 계약으로 다루기

MQTT QoS 1만으로 DB 반영을 보장한다고 보지 않았습니다. 저장 실패에는 보존 확인을 보내지 않고, 같은 데이터의 재수신에 다시 응답할 수 있도록 했습니다. 현재 장비 원본은 RAM에 보관하므로 전원 중단 이후의 복구는 별도 개선 범위입니다.

RESULT

개발 결과

정상·불완전 세션, 동일 재전송, 수온·측정 시점 충돌, 커밋 실패 시 확인 미발행을 다루는 단위·통합 테스트를 구성했습니다. 실물 정상 인수에서는 서버 보존 확인 후 장비가 버퍼를 해제하는 흐름을 확인했습니다.

FEATURE 04 구현·개선 진행 중

Android 재배 앱

센서 수치만 나열하는 화면에서, 식물별 측정 추세와 물 관리 이력을 함께 보는 앱으로 확장했습니다.

PROBLEM

문제

단일 측정값만으로는 어떤 식물의 기록인지, 물 교체나 보충 전후에 값이 어떻게 달라졌는지 파악하기 어려웠습니다. 실제 센서와 모의 측정, 과거 가정 수온의 기록도 섞이지 않아야 했습니다.

SOLUTION

해결

Kotlin·Jetpack Compose로 재배 대시보드, 측정 시작·결과, 기간별 TDS 차트와 날짜별 관리 이력을 구현했습니다. 재배 시작 시 측정 대상을 고정하고 물 교체·보충·영양제 추가를 기록합니다. 차트는 실측 정상 기록의 세션 중앙값을 보여주고, 모의 측정은 실측 추세에서 제외합니다.

설계 이유와 트레이드오프

차트와 이력의 조회 범위 제한

기간별 조회에 페이지 수와 시간 예산을 두고, 전체 기간을 다 가져오지 못한 경우 화면에 알립니다. 관리 이력과 측정 이력을 나눠 필요한 기록부터 확인할 수 있게 했습니다.

인증과 쓰기 요청의 불확실성도 앱에서 관리

개인용 단일 계정 인증을 적용하고, 인증 만료나 통신 실패 때 결과가 확정되지 않은 요청의 키·본문을 보존합니다. 단순 화면 테스트뿐 아니라 로그인·측정·재배 관리 흐름을 격리 환경에서 확인하도록 했습니다.

RESULT

개발 결과

재배 등록·종료, 측정·결과 조회, TDS 기간 차트와 물 관리 이력을 구현했습니다. Android JVM·UI 테스트와 전용 API·DB·MQTT를 사용한 종단 테스트를 구성했고, 최근에는 재배 정보 편집과 상세 이력의 스크롤 동작을 개선했습니다.

FEATURE 05 구성·개발에 적용

에이전트 하네스

AI에 기능을 한 번 요청하는 방식에서, 작업 범위와 인수 조건을 정하고 구현·검증·수정을 이어가는 개발 체계로 바꿨습니다.

PROBLEM

문제

펌웨어·백엔드·앱을 함께 개발하면서 대화만으로 요구사항을 전달하면, 실제 구현 상태와 승인 범위가 흐려지고 실패한 검증을 놓치기 쉬웠습니다.

SOLUTION

해결

AGENTS.md에 유지할 설계와 작업 규칙을 두고, Harness.md와 기능별 작업 명세에 계획·인수 조건·검증·실패 시 중단 기준을 정리했습니다. 저는 제품 목표와 주요 설계를 결정하고 실물과 결과를 검수하며, 에이전트는 승인 범위의 구현·테스트·오류 수정·인계를 순차 수행하도록 구성했습니다.

설계 이유와 트레이드오프

자율 구현과 승인 경계 분리

구현 단계마다 검증을 이어가되 범위 밖의 아키텍처·인프라 변경과 운영 배포·Git 발행은 별도로 다룹니다. 단계당 수정 횟수와 동일 원인 반복 실패의 중단 기준도 두었습니다.

문서 규칙과 실제 자동 검증 구분

백엔드 단위·PostgreSQL 통합 테스트, 펌웨어 계산 호스트 테스트, Android JVM·Lint·UI·종단 테스트를 연결했습니다. 문서에 적은 모든 규칙이 자동으로 강제된다고 보지 않고, 실제 검사와 사람의 검수 범위를 구분했습니다.

RESULT

개발 결과

센서 도메인 전환, 수온 보정, 서버 자동 측정과 Android UI 개선에 같은 작업 명세·순차 구현·검증·인계 흐름을 적용했습니다. 장비부터 서버·앱까지 AI와 개발하되, 제품 방향과 실물 배포·사용 결과는 직접 확인하는 경험을 쌓았습니다.

FEATURE 06 개인 서버 배포·사용

미니 PC 배포

직접 조립한 장비를 개인 Ubuntu 미니 PC와 연결하고, Android 앱에서 HTTPS로 사용하는 서비스로 배포했습니다.

PROBLEM

문제

PC에서 가상 데이터로 동작하는 것과, 실제 센서·개인 서버·휴대폰을 연결해 사용하는 것은 다른 문제였습니다. MQTT 장비 통신과 외부 앱 접근, 비밀 설정과 배포 산출물의 경계가 필요했습니다.

SOLUTION

해결

미니 PC에 Spring Boot·PostgreSQL·Mosquitto와 Cloudflare Tunnel을 Docker로 구성하고 직접 배포했습니다. 장비는 LAN 전용 TLS MQTT와 인증·ACL을 사용하고, 앱은 HTTPS API와 단일 계정 인증으로 접근하도록 구성했습니다.

설계 이유와 트레이드오프

장비 통신과 앱의 외부 접근 구분

MQTT는 장비가 있는 LAN에서 사용하고 외부 앱 접근은 Tunnel을 통한 HTTPS API로 제한했습니다. 테스트는 운영 데이터 대신 전용 DB·브로커를 사용하도록 구성했습니다.

구현 검증과 운영 적용을 별도로 확인

서버 배포는 직접 수행하고, 에이전트의 로컬 빌드·검증 결과와 실제 서버·장비·앱의 동작을 나눠 확인했습니다. 매시간 자동 측정은 기본 OFF와 명시적 장비·재배 설정으로 구현했으며, 장기 운영 안정성은 후속으로 점검합니다.

RESULT

개발 결과

미니 PC 서버와 앱을 배포하고 실물 수온 측정부터 보정값 저장·앱 표시까지 연결했습니다. 자동 측정의 회차 중복·수동 측정 충돌·오프라인 처리는 격리 환경에서 검사했으며, 실제 정각 회차와 장기 운전 확인은 이어갈 계획입니다.
